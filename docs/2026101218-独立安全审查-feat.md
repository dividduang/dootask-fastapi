## 3. 有证据发现（按严重度）

### R1 / P1：被ACL拒绝的旧投递阻塞撤权tombstone与新通知

- 发现时位置：`backend/realtime.py:_pending`，50–55；调用链 `dialog_core.sync_members → enqueue_push → jobs._push → _reconnect → _pending → delivery_loop`。
- 触发：成员离线期间某群产生至少200条消息；在他上线前移除该成员，同事务的unscoped groupExit排在旧消息之后。
- 证据：SQL先order_by(id).limit(200)，再在Python按当前scope/ignore_fds过滤；被过滤记录仍transport_sent_at=NULL，不退休、不推进游标。每次poll永远得到同200条，权限复验虽然正确，却饿死后面的groupExit及其他有权消息，直至一天有效期过去。客户端缓存不能及时收到撤权删除。不是泛指丢Redis唤醒。
- 最小修复：同Connection显式discard无权限/ignored项，或越过拒绝项分页扫描；不能删ACL检查、把它们当已发送、伪ACK。
- Owner：IntegrationOwner。后续已报告添加`discarded_at/discard_reason`并在pending/reconnect查询排除；已读新状态consumer，拒绝项写`scope_revoked/ignored_fd`，没有写ACK。
- QA：真实两用户离线200+记录→撤权→重连，检查旧敏感payload不发、groupExit及另一会话新消息能继续投递；同时检查transport_sent与ack不同。

### R2 / P2：机器人短Token耗用登录设备配额并驱逐真实登录

- 发现时位置：`backend/domains/messaging_jobs.py:_short_token`，29–32；`auth.issue_token`，179–182。
- 触发：有效登录用户正常发200条触发机器人Webhook的消息（更多机器人会更早达到配额）。
- 证据：`bot_prepare`给bot及人类sender调用交互`issue_token`，每次新增user_devices，并撤销最新200条以外旧设备；这里只缩session为1小时，设备expiry仍默认30天。原登录设备被后台驱逐，HTTP/WS真实会话失效。源User.php的generateTokenNoDevice不记录持久设备，源BotReceiveMsgTask给人类sender用该入口。
- 最小修复：短服务token不占交互device配额，但保留过期、userid/email/generation、停用和撤销。
- Owners：IndependentIdentity拥有auth helper，IntegrationOwner拥有SQL与Messaging调用处。后续已报告`purpose=service,device_id=NULL`、1小时硬上限及跨消费认证分支；已读authenticate与refresh/logout/改密对应分支，未知purpose不被允许、service不refresh。
- QA：真实205次短发行前后user_devices不增，交互token仍有效；服务token过期/改密代次/退出/停用均拒绝；服务token不能通过QR/邮箱/刷新升级成长期token。

### R3 / P2：DAV认证与HTTP凭据撤销ABBA死锁

- 发现时位置：`backend/domains/filedav.py:authenticate_dav`，217–222；`credential`，84–88；`auth.authenticate`用户行锁。
- 触发：同账号同一DAV应用凭据的DAV请求与HTTP file/dav/revoke并发。
- 证据：DAV先凭据FOR UPDATE后用户锁；HTTP actor认证先用户锁后凭据FOR UPDATE。各持一锁相互等待，MariaDB中止一方；API变503，DAV无SQL死锁捕获时500，撤销/文件操作失败。源DAV认证没有这组逆向锁。
- 最小修复：统一用户→凭据，先发现owner再取得账号/凭据锁，锁后复核owner/撤销/过期/密码；不能省略复核来消竞态。
- Owner：IntegrationOwner。后续已报告并读到按owner发现→user lock→credential FOR UPDATE且重查owner/status的顺序。
- QA：真实并发认证/revoke与PUT，撤销提交后认证拒绝，不能靠重跑单线程掩盖锁序。

### R4 / P2：管理员重置密码先写凭据后锁目标账号

- 发现时位置：`backend/domains/account_admin.py:operation`，174–178目标用户无锁读取，password分支218–220先写凭据；`accounts.mutate_user`后写users；`auth.change_password`先authenticate用户锁后写凭据。
- 触发：管理员重置目标密码与目标本人改密并发。
- 证据：管理员先占目标凭据锁再等目标用户锁；本人先占目标用户锁再等同一凭据锁，造成ABBA事务失败。管理员自身账号锁不等于目标账号锁。
- 最小修复：读取目标用户时先锁目标users，并将该账号凭据/设备变更统一账号→凭据/设备顺序。
- Owner：IndependentIdentity。1216报告已明确`lock_user`收敛管理员重置/删除/bot token/撤销；审查未运行并发回归。
- QA：两个实际Connection并发管理员reset与本人editpass；检查没有死锁引起500/503、只有有效代次保留、旧token全部被撤销。

### R5 / P2：成员变化遗漏历史消息搜索权限观察者

- 发现时位置：`backend/domains/dialog_core.py:sync_members`，122–128；消费侧`search.document/allowed_users(message)/run_search`。
- 触发：群旧消息先入Manticore索引，然后新增成员B；B可get_dialog/读历史，但搜索旧消息。
- 证据：索引allowed_users只在search.sync时读取当时member_ids；Manticore候选查询先ACL过滤，旧allowed_users不含B，DB最终复验不能补回根本没进候选的旧消息。源WebSocketDialogUserObserver在create/delete均dispatch update_dialog_allowed_users。反向撤权查询有DB终审，不把它夸大为已证实数据泄漏。
- 最小修复：同业务事务派真实批量刷新既有消息allowed_users任务，显式注册consumer；不只刷新新消息、不移除DB ACL复验。
- Owner：IntegrationOwner。后续已报告`sync_members → search.dialog_members`；实际读取consumer `sync_dialog_members` 249–262更新backend_message MVA，register_jobs 400有显式注册，main生命周期装search registrar。
- QA：真实Manticore下旧消息→加B→任务成功→B能搜；移除B后旧索引尚未刷新期间仍不能通过最终DB ACL返回。

### R6 / P2：ZIP/Messaging系统机器人consumer漏迁移，首次功能永久失败

- 发现时位置：`backend/domains/files_jobs.py:pack`，61–65；同类`dialog.py:_bot`，425–430。
- 触发：全新库用户首次上传/打包，尚未通过其他功能创建system-msg；首次匿名/系统机器人发送同样受旧lookup-only入口影响。
- 证据：新account_meetings.bot_get已经独立按需建真实bot，但pack仍只查询，缺bot即异常。它在ZIP/ready更新之后抛错，jobs.savepoint把ready/通知回滚并永久重试，下载不可用。Messaging lookup仍返回BLOCKED_LICENSE。源FileController1268是botGetOrCreate。此发现是**独立系统真实消费者未切换**，不是要求商业授权、不是建议绕过对象安全。
- 最小修复：两个consumer复用已存在的独立bot_get并复核停用，不另建bot实现或虚假fallback。
- Owner：IntegrationOwner，bot创建helper归IndependentIdentity。后续已报告两consumer已共用bot_get；运行未测。
- QA：空新库正常注册、上传、pack，无预种bot和无厂商许可；ready、进度、完成模板、ZIP字节真实，失败回滚且无假成功；停用bot不能发消息。
