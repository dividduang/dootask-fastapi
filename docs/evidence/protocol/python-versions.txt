<section id="status-key">
<span id="version-status-key"></span><h2>Status key<a class="headerlink" href="#status-key" title="Link to this heading">¶</a></h2>
<p>Python releases go through five phases, as described in <span class="target" id="index-19"></span><a class="pep reference external" href="https://peps.python.org/pep-0602/"><strong>PEP 602</strong></a>.  Release
managers can adjust specific dates as needed.</p>
<dl class="field-list simple">
<dt class="field-odd">feature<span class="colon">:</span></dt>
<dd class="field-odd"><p>Before the first beta, the next full release can accept new features,
bug fixes, and security fixes.</p>
</dd>
<dt class="field-even">prerelease<span class="colon">:</span></dt>
<dd class="field-even"><p>After the first beta, no new features can go in, but feature fixes
(including significant changes to new features), bug fixes, and security fixes
are accepted for the upcoming feature release.</p>
</dd>
<dt class="field-odd">bugfix<span class="colon">:</span></dt>
<dd class="field-odd"><p>Once a version has been fully released, bug fixes and security fixes are
accepted. New binaries are built and released roughly every two months. This
phase is also called <strong>maintenance</strong> mode or <strong>stable</strong> release.</p>
</dd>
<dt class="field-even">security<span class="colon">:</span></dt>
<dd class="field-even"><p>After two years (18 months for versions before 3.13), only security
fixes are accepted and no more binaries are released.  New source-only versions
can be released as needed.</p>
</dd>
<dt class="field-odd">end-of-life<span class="colon">:</span></dt>
<dd class="field-odd"><p>Five years after a release, support ends. The release cycle is
frozen; no further changes are allowed.</p>
</dd>
</dl>
<p>See also the <a class="reference internal" href="../developer-workflow/development-cycle/#devcycle"><span class="std std-ref">Development cycle</span></a> page for more information about branches and backporting.</p>
