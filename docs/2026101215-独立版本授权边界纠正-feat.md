# 独立版本授权边界纠正

## 用户原话与决策
用户在授权材料询问中明确：**“重构就是为了 不要他的授权”**。
PM据此纠正之前把原厂商业授权视为新系统硬门禁的过度约束：交付目标为不依赖原厂商业授权服务的全新FastAPI系统，而非兼容或伪造原厂商业版。

## 当前有效要求
1. 新系统自行管理本地账户、注册、管理员创建、机器人、部门和设备，不需要doo.so、原厂设备绑定或商业席位验证。
2. 不伪造原厂license、不冒充原厂商业授权、不patch私有二进制或利用原厂在线服务。独立系统身份必须如实表述。
3. 所有用户对象安全仍保留：密码哈希、会话过期/撤销、禁用、邀请/邮箱/LDAP策略、管理员权限、速率限制及首次初始化竞态控制；移除商业门禁不是移除身份认证和访问控制。
4. 新库/新账号决策不变，不导入旧数据。前端原件继续保留，默认不修改Vue/静态制品。
5. 原厂购买/激活/试用/离线license导入不再是本新系统需要连接的服务。既有前端页面的兼容处理必须明确呈现独立部署状态，不返回“原厂专业版已授权”的虚假声明。若原样页面无法诚实表达，须将具体冲突交PM，不偷偷篡改前端或掩盖失败。
6. 开源许可证、版权、第三方notice、修改声明与对应源码提供义务不因去原厂商业依赖而消失。保留现有法律文本；不将工程结论冒充法律认证。

## 历史文档适用性
1201–1214及成员证据中的BLOCKED_LICENSE/native注册门禁，记录的是用户本次澄清之前的实施假设，保留作为审计历史，不篡改旧证据。当前代码和交付状态应以本决策后的新报告/覆盖清单为准；必须清掉新实现中因此产生的永久失败占位、死代码和厂商授权调用，不留双重模式/开关。

- 独立身份切换成员：跨shared auth、accounts/机器人/system/license、files授权接口完成清洁切换，真实注册/创建和前端兼容响应；不动main/数据库核心。

- 独立审查成员：认证/对象权限/文件路径/消息scope与协议互操作风险，只给有源码证据的具体发现，由所有者修复。
- 实现冻结后统一独立启动和真实UI/API/WS/文件/持久化验收。当前代码清单不等于任何运行通过。

## 用户进一步确认：仅授权UI例外
- 在明确说明原页面硬编码厂商设备码/登录状态后，用户选择 **移除原厂授权界面**：仅移除原厂授权、购买、试用入口和商业提示，其他页面、样式、功能保持原样。
- IndependentIdentity获此限定前端写权限；须同时处理源码和实际加载制品，不能只CSS隐藏、注入宿主shim或改源码未更新制品。原LICENSE/notice/对应源码获取义务不删。
- 既有4006原件hash基线仍是迁移前基线；本次获准例外的每个源/制品变化应另列hash及来源，不再虚称所有交付文件零改动。

- SecurityReview发现DAV credential→user与HTTP撤销user→credential锁序冲突；IntegrationOwner负责统一并在锁后重新检查撤销，留并发回归。

- 共享改密新增settings参数未被main传入的问题已由整合者确认修正，仍须真实改密运行检查；不以修复声明当通过。
